# Veloce

A **low-bit, zero-allocation programming language and AOT compiler for LLM
inference**, implementing the PRD and ERD in this repository.

Veloce treats sub-byte quantization as a first-class language feature, removes
imperative loops from tensor code, plans every buffer at compile time into a
static arena, and lowers ternary (1.58-bit) matrix multiplies to integer
add/sub. The compiler emits portable **C11** that builds into a self-contained
object with no runtime dependency.

```
 .vel source ──► lexer ─► parser ─► type/shape checker ─► static arena planner ─► C11 codegen ─► cc -O3 -march=native
                     │                 │                        │                      │
                 declarative      sub-byte dtype          liveness + buffer        static inline kernels,
                 tensor algebra   & shape inference       reuse (peak memory)      mmap'd weight blobs
```

## Quick start

```bash
# Compile a module to C
./velocec emit examples/transformer_block.vel -o build/tb.c

# Inspect the plan (trit matmuls, arena reuse)
./velocec check examples/transformer_block.vel

# Dump the compiler's internal entity graph (ERD.md entities)
./velocec erd examples/transformer_block.vel --format mermaid

# Build & run the tiny-LM inference demo
make demo

# Run the full test-suite (compiles + runs real C, checks vs. NumPy)
# (first run auto-creates .venv and installs NumPy from requirements-test.txt)
make test

# End-to-end examples: transformer vs NumPy, KV-cache decoding, and
# train -> ternarize -> deploy
make examples
make kv
make train

# Measure real kernel/model throughput against the PRD targets
make bench-throughput

# Print the capability model card embedded in a .veloce export
./velocec model-card examples/tiny_lm.veloce
```

## A taste of Veloce

```veloce
module transformer_block

dim T = 4
dim D = 16
dim F = 32

fn attention(q: f32[T, D], k: f32[T, D], v: f32[T, D]) -> f32[T, D] {
    let kt = transpose(k)            # [D, T]
    let scores = matmul(q, kt)       # [T, T]
    let probs = softmax(scores * 0.25)
    return matmul(probs, v)          # [T, D]
}

fn mlp(x: f32[T, D], w1: trit[F, D], w2: trit[D, F]) -> f32[T, D] {
    let h = matmul_trit(x, w1)       # [T, F]  — add/sub only, no multiply
    let a = silu(h)
    return matmul_trit(a, w2)        # [T, D]
}
```

No `for`/`while` loops in tensor code. `trit` weights are stored packed
(5 trits per byte); `matmul_trit` lowers to integer addition/subtraction.

## Performance (measured, 4-vCPU dev VM)

`make bench-throughput` runs compiled C against the real `veloce_runtime.h`
kernels. Representative result:

| Metric | Measured | PRD target |
|--------|----------|------------|
| trit GEMV 4096×4096 (1 thread → 4 threads) | 9.2 → 26.1 GMAC/s (**2.84× speedup**) | — |
| trit GEMV read bandwidth | 5.2 GB/s = **27% of peak** (decode-bound, see below) | — |
| trit GEMV, four rows per pass vs one neuron at a time | **1.30–1.34×** median of 3 runs (K = 1024, 1536, 4096) | — |
| trit GEMV, two tokens per call vs one (shared weight pass) | **1.25–1.41× per token** (4096²: 7.59 → 10.71 GMAC/s, 2.21 → 1.57 ms/token) | — |
| trit GEMV, four tokens per call vs one (quarter the weight traffic) | **1.63× per token** (4096², one thread: 8.6 → 13.5 GMAC/s per token, 1.94 → 1.19 ms/token) | — |
| attention block (QK^T + softmax + AV) | ~31–35 GFLOP/s | — |
| **end-to-end 275.6M ternary decoder** (6L, d=1536, ffn=6144, V=32000) | **25–34 tok/s on one thread, 62.9 tok/s on four** (15.9 ms median; host-load dependent) | — |
| same model, **KV-cached** decode (32 tokens, 64 slots/layer, 2 tokens/call) | **33.7 tok/s on one thread, 63.6 on four** (15.7 ms/token, verify rel err 1.3e-6) | — |
| projected 7B-class decode | **4.03 tok/s** (compiled layer: 5.44 tok/s) | ≥ 15 tok/s (**3.7× short**) |
| weight footprint (7B-class) | 1.3 GB vs 13.2 GB fp16 (90% saved) | ≥ 80% smaller ✅ |
| compile time | ~4 ms | < 2 s ✅ |
| heap allocation in generated C | none | zero ✅ |

The 7B-class speed gap is NOT purely memory bandwidth, and the earlier claim
that the kernel sat at the bandwidth roofline was measurement error. The old
"streaming peak" was a scalar single-threaded byte-sum loop; the real ceiling
this VM can stream is **19.5 GB/s at 4 threads** (6.0 GB/s at 1, both
host-load dependent); its roofline is therefore 14.8 tok/s for the 7B class.
Against that the trit GEMV achieves **5.2 GB/s — 27% of peak**, so it is
*decode* bound, not bandwidth bound: every packed byte needs a byte load plus
a 32-byte LUT load for only 5 useful values.

The kernel now works on four output rows per pass. Flat base-3 packing puts
row j at byte `(j*K)/5` slot `(j*K)%5`, so rows only share an `x` window when
they are in the same byte phase; the kernel runs rows `j, j+p, j+2p, j+3p`
(`p = 5/gcd(K,5)`) and feeds one pair of 32-byte `x` loads to four LUT loads
and four FMAs instead of re-reading `x` for every output neuron. Same-process
back-to-back measurement puts that at **1.30–1.34×** (median of 3 runs at
K = 1024/1536/4096), and end to end at 23.6 tok/s versus 22.3. What remains is
one byte load plus one 32-byte table load per five MACs — about three load
slots per five MACs on this EPYC, whose 128-bit FP units split 32-byte loads in
two — so ~3.3 MAC/cycle is the current wall.
`benchmarks/bench_gemv_roofline.py` measures all of this directly (a dense f32
FMA runs 1.5–2× the GEMV's MAC rate while reading 4× the bytes). Closing the
rest is real optimization headroom, not a hardware wall; the 9.5–15.8 tok/s
roofline printed above is only reachable once the decode stops being the
bottleneck.

The mid-size number is a *real* end-to-end run, not a projection:
`benchmarks/bench_midi_lm.py` generates a 275.6M-ternary-parameter decoder with
deterministic weights, writes it as a `.veloce` file, renders the module with
`veloce/lmmodule.py` (the same text as `examples/midi_lm.vel`, which a test
keeps in sync), compiles it and times the generated C against the mmap'd file.
`--config D=2048 --config F=5632 --config layers=7` measures a second,
0.5B-shaped network from the same command; `make bench-midi-05b` does it. On
one thread the model sustains ~7.7 GMAC/s — the same rate as the standalone
kernel — so it runs at the kernel's compute roofline, and streams 55 MB of
packed trits per token at ~1.4 GB/s. Four threads take it to **62.9 tok/s**
(15.9 ms/token), 2.5× the one-thread rate. Decoding 32 tokens through a
64-slot per-layer KV cache runs at **63.6 tok/s on four threads** (15.7
ms/token, 33.7 on one) with a 1.3e-6 relative error against the NumPy
reference. The cached driver decodes **two
tokens per call**, so the attention mask carries one row per query row
(`i32[T, CT]`) and different rows hide different slots -- a mask read as a
single broadcast row would change the logits. The two tokens also share one
weight pass: the two-row GEMV decodes each packed byte and LUT row once and
feeds both query rows from it, which is where the 0.99× → 1.37× came from,
and its result is bit-identical to two one-row passes (tested). Four tokens
per call now run a four-query kernel: two output rows at a time, 16
accumulators, each packed byte and LUT row shared by all four rows — 4096² measures
1.94 → 1.19 ms per token (1.63×, one thread, three runs), bit-identical to
four one-row passes. Until 2026-11-20 four threads were *slower* than one: the work split
clamped the chunk to `VELOCE_PAR_GRAIN` *elements*, which handed every loop
with fewer than 512×lanes items to a single worker (a 4096² two-row GEMV ran
at 1.06 CPUs utilised). With the grain treated as a byte budget, four threads
now scale the decode 2.5× and the cached decode 1.89×; the rest of the
shortfall is the kernel's decode-bound inner loop, not the team.

The VM is shared, so numbers vary run to run; every benchmark reports medians
and best-of-N, plus a same-run streaming-bandwidth probe so a tok/s figure can
be read against what the host can actually deliver.

`benchmarks/results.json` and `benchmarks/midi_lm_results.json` hold the last
full runs; the midi_lm file carries the eager *and* cached (KV-cache) numbers
in one place. All are stamped with `measured_at` (UTC) and the CPU they were
taken on, because a figure is only comparable against the host state that
produced it. `make bench-midi` regenerates the midi_lm artefact with
`--cached --cached-chunk 2`, so the cache block cannot go missing again and
the recorded decode goes through the per-row mask kernel rather than the
broadcast one.

## Serving & export scope

Two export/serving paths exist and both are exercised by a `make` target:

| Path | Scale | Command |
|------|-------|---------|
| QAT train → ternarize → pack → compile → mmap-deploy | 26.9k params (92% ternary) | `make train` |
| Production packing → `.veloce` → mmap'd forward pass | 275.6M ternary params | `make bench-midi` |

`make train` is the full quantization-aware-training loop: a NumPy trainer
trains with a straight-through ternary estimator, `weights.save_veloce` writes
the packed file, `velocec` compiles the `.vel` module to C, and the resulting
binary memory-maps the weights and serves predictions (32/32 match the NumPy
reference). `make bench-midi` takes the same export path at 275.6M parameters
and measures real decode throughput from the memory map.

Not implemented: QAT at 100M+ parameter scale. Training a 275M-parameter
model needs GPUs and days; the mid-size harness therefore uses deterministic
pseudo-random weights and measures *throughput*, not quality. The serving
runtime, packing, and mmap path are identical either way, so a QAT-trained
checkpoint at that scale would drop into the same `.veloce` file format.

## Model capability defaults

Every `.veloce` export carries a **capability model card**. The default profile
defines four pillars — deeper specialist knowledge, richer world
understanding, stronger coding and agentic behaviour, and real-world task
focus — each with a status of `declared`, `trained`, or `verified`. `trained`
and `verified` require attached evidence; `declared` is explicitly not a
capability claim. The compiler enforces this when writing and reading cards:

```bash
./velocec model-card examples/tiny_lm.veloce   # prints the embedded card
```

Both current checkpoints (the 27k-parameter QAT classifier and the 275.6M
throughput demonstrator) declare all four pillars at `declared`. Veloce is the
inference compiler — the capabilities themselves come from the trained model,
not from the language. See [`docs/model-capabilities.md`](docs/model-capabilities.md)
for the full contract and the metrics each pillar is evaluated with.

See [`docs/implementation-status.md`](docs/implementation-status.md) for the
exact FR-by-FR mapping and [`docs/language.md`](docs/language.md) for the
language reference.

## Design notes

* **Compute dtype is `f32`; `trit`/`fp16` are storage dtypes** — activations
  stay in float, weights are quantized on disk and decoded/used in the kernel.
  This mirrors real low-bit inference engines.
* **Trit packing is flat, base-3, 5 per byte** — the same layout the C runtime
  writes and the `.veloce` file stores, so mmap'd weights are used in place.
* **`matmul_trit(x, w)` takes `w` shaped `[out, in]`** (the LLM weight layout)
  so the reduction runs over `in` and lowers to `acc += x[k]` / `acc -= x[k]`.
* **The arena is per-function `static`** — a direct realisation of "0 bytes
  allocated on the heap during inference".

===== PRD.md =====
Product Requirements Document (PRD)
​Project Name: Veloce (Low-Bit, Zero-Allocation LLM Programming Language & Compiler)
Version: 1.0
Status: Draft / Architectural Blueprint
​1. Executive Summary
​Veloce is a domain-specific programming language (DSL) and ahead-of-time (AOT) optimizing compiler engineered specifically for Large Language Model (LLM) development, quantization, and inference. Unlike general-purpose languages (Python, C++, Rust) that suffer from abstraction overhead, dynamic memory fragmentation, deep nested loops, and heavy reliance on discrete GPUs, Veloce treats sub-byte quantization (e.g., 1.58-bit ternary, 4-bit integer) as first-class primitives, eliminates explicit looping via declarative tensor algebra, and enforces static compile-time memory planning.
​2. Problem Statement
​Modern LLM development faces critical bottlenecks:
​1. Memory Wall: High-precision weights (fp16/fp32) and unoptimized KV-caches require massive VRAM/RAM, pricing out edge and commodity CPU hardware.
​2. GPU Lock-in: Current frameworks rely heavily on proprietary GPU ecosystems (e.g., CUDA) for acceptable throughput.
​3. Compute & Loop Overhead: Imperative nested loops cause severe CPU cache misses, while fragmented frameworks introduce kernel-launch and intermediate memory-read/write bottlenecks.
​4. Language Complexity: Existing systems languages impose steep cognitive loads (borrow checkers, complex template metaprogramming, async function coloring) that slow down AI engineering iteration.
​3. Goals & Success Metrics
​Memory Footprint Reduction: Reduce runtime RAM usage by \ge 80\% compared to fp16 PyTorch baselines via native trit (1.58-bit) packing and static buffer reuse.
​Hardware Independence: Achieve real-time token generation (\ge 15\text{ tokens/sec} on 7B-class ternary models) on standard multi-core CPUs (x86 AVX-512 / ARM NEON) without a discrete GPU.
​Zero Runtime Allocation: 0\text{ bytes} dynamically allocated on the heap during the inference loop.
​Compilation Speed: Compile standard Transformer architectures in < 2\text{ seconds}.
​4. Target Audience
​AI Systems Engineers: Building ultra-fast inference engines for edge devices, mobile hardware, and CPU-only cloud instances.
​LLM Researchers: Experimenting with extreme quantization (BitNet / 1.58-bit), custom attention mechanisms, and MatMul-free architectures without writing raw C++ intrinsics.
​5. Core Functional Requirements
​5.1 First-Class Sub-Byte Type System
​FR-1.1 Native Low-Bit Primitives: Support trit (\{-1, 0, 1\}, 1.58-bit), i2, i4, fp8, and fp16 as built-in scalar and tensor element types.
​FR-1.2 Automatic Bit-Packing: The compiler must automatically pack multiple sub-byte values into contiguous machine words (e.g., packing 5 trit values into a single u8 byte) at compile time or model load time without manual bitwise operations from the user.
​FR-1.3 MatMul-Free Lowering: Matrix multiplications involving trit tensors must automatically lower to pure integer addition/subtraction (ADD/SUB) instructions, bypassing floating-point multipliers.
​5.2 Loop-Free Declarative Tensor Algebra & Kernel Fusion
​FR-2.1 Declarative Syntax: Eliminate imperative for/while loops for tensor operations. Provide native Einstein-summation (einsum) and linear algebra operators (@, *, +).
​FR-2.2 Automatic Operator Fusion: The compiler IR must detect contiguous element-wise and reduction chains (e.g., RMSNorm -> Linear -> SiLU -> ResidualAdd) and fuse them into a single hardware-level loop pass inside CPU registers, eliminating intermediate RAM round-trips.
​FR-2.3 Implicit Vectorization: Automatically map fused kernels to target SIMD instruction sets (AVX2, AVX-512, ARM NEON/SVE).
​5.3 Static Memory Arena & Zero-Copy I/O
​FR-3.1 Static Liveness Analysis: Compute exact tensor lifetimes across the computation graph at compile time.
​FR-3.2 In-Place Buffer Reuse: Assign non-overlapping tensor activations to the exact same physical memory offsets within a pre-allocated static Arena, bounding peak activation memory to the size of the single largest layer.
​FR-3.3 Zero-Copy Model Loading: Support direct mmap loading of serialized .veloce weight binaries whose on-disk byte alignment matches the compiler's internal packed memory layout.
​5.4 Hardware-Agnostic Backend & Concurrency
​FR-4.1 Multi-Target Codegen: Lower the optimized Intermediate Representation (IR) to LLVM IR / C23 with SIMD pragmas, supporting x86_64, ARM64, and optional Vulkan/WebGPU compute shaders.
​FR-4.2 Implicit Cache-Aware Parallelism: Automatically partition tensor workloads across physical CPU cores based on L1/L2/L3 cache topology without user-managed threads or async/await.
​6. Non-Functional Requirements
​Determinism: Execution time and memory footprint must be 100% deterministic across runs.
​Minimal Toolchain: Distributed as a single standalone compiler binary (velocec) with zero external runtime dependencies.
​Interoperability: Direct C ABI compatibility (extern "C") so compiled models can be embedded into Rust, Go, C++, or Python hosts effortlessly.
​7. Default Model Capability Profile
​Every model built with Veloce declares a standard capability profile in its .veloce model card, targeting four pillars:
​
​- Deeper knowledge: more accurate answers in specialist topics.
​- Richer world understanding: real-world context reasoning, not just text patterns.
​- Stronger coding and agentic: plan, call tools, complete multi-step tasks.
​- Real-world task focus: complex coding, front-end builds, professional workflows.
​
​The profile is declarative: each pillar carries a status of declared, trained, or verified, and trained/verified claims require attached evidence. The compiler and runtime cannot supply these capabilities on their own; they come from the trained model (data, scale, post-training, evaluation). See docs/model-capabilities.md.
​
​8. Out of Scope (v1.0)
​Dynamic computational graphs (eager execution mode).
​Distributed multi-node training across clusters.
​General-purpose OS abstractions (networking, GUI, file-system management beyond model mmap).
​Training or fine-tuning at 100M+ parameter scale (the v1.0 toolchain exports and serves such models; producing their weights is out of scope).

2. Core Entity Descriptions

Entity Role in Compiler / Runtime
MODULE The top-level compilation unit representing an LLM architecture and its hardware compilation target (CPU SIMD capabilities and cache line size).
DATA_TYPE & PACKING_RULE Defines sub-byte primitives (trit, i4, etc.) and the exact mathematical bit-packing layout (e.g., base-3 encoding of 5 trit values into 1 uint8) so the compiler generates branchless unpacking instructions.
IR_NODE Represents a declarative mathematical operation in the Directed Acyclic Graph (DAG), completely free of explicit user-written loops.
FUSED_KERNEL Represents a merged subgraph of consecutive IR_NODEs (e.g., Normalization + Linear Projection + Activation) compiled into a single register-resident loop.
MEMORY_ARENA & MEMORY_SLICE Models the static memory planner. birth_step and death_step track tensor liveness so non-overlapping TENSOR_DESCRIPTORs share identical byte_offset addresses inside the MEMORY_ARENA.
WEIGHT_ASSET & PACKED_BLOCK Maps quantized model weights directly from disk (mmap) into aligned memory blocks matching the compiler's expected SIMD register layout without runtime deserialization.

# The Veloce Language (v1.0)

Veloce is a statically typed, ahead-of-time language for describing LLM
inference graphs. Tensor code is declared, not looped over.

## Module

```veloce
module my_module

dim T = 4          # bind symbolic dimensions to concrete sizes (required)
dim D = 16
dim F = 32
target "x86_64_avx512"   # optional; recorded in the MODULE entity
cache 64                 # optional; cache-line bytes, recorded in the MODULE
```

Every symbolic dimension used in a type must be bound by a `dim` at the top of
the module, because the compiler sizes all buffers statically.

## Execution model

Veloce programs are implicitly parallel: the compiled kernels partition
independent output elements (rows of a matmul / normalisation, elements of an
elementwise op) across the machine's CPU cores. There are no user-visible
threads, and every output element is accumulated by exactly one worker in a
fixed order, so results are bit-identical for any number of threads.

Threading is selected at build time by the compiler driver:

| Build | Backend | Dependency |
|-------|---------|------------|
| `velocec build ...` with OpenMP-capable `cc` | OpenMP (`-fopenmp`) | toolchain runtime |
| `velocec build ...` without OpenMP | C11 `<threads.h>` pool | libc only |
| `-DVELOCE_POOL=0` | serial | none |

Compile-time knobs: `VELOCE_THREADS=n` pins worker count, `VELOCE_PAR_MIN`
(default 1024) sets the minimum tensor size before threading, `VELOCE_PAR_GRAIN`
(default 512) is the largest number of output elements one worker is handed —
it is applied as a byte budget (a quarter of L2, expressed in items, capped by
the element count), because a task size measured in elements alone collapses
small-element loops onto a single worker — and `VELOCE_POOL_SPIN` sets how long
an idle worker spins before sleeping.

## Types

| Type | Meaning |
|------|---------|
| `f32` / `fp32` | 32-bit float (the compute dtype for all activations) |
| `fp16` | 16-bit float, storage |
| `trit` | 1.58-bit ternary `{-1, 0, +1}`, packed 5-per-byte, storage |
| `i4` | 4-bit signed integer, packed 2-per-byte, storage (`matmul_i4`) |
| `i8`/`u8`/`i2` | small integers (storage; `i2` has no packed kernel yet) |
| `i32`/`i64` | scalars |
| `T[N]` | 1-D tensor |
| `T[R, C]` | 2-D tensor |

Tensors may be 1-D or 2-D. Dimension entries are integer literals or symbolic
names bound by `dim`.

## Functions

```veloce
fn name(a: f32[T, D], b: trit[D, D]) -> f32[T, D] { ... }
fn pair(x: f32[D]) -> f32[D], f32[D] { ... }   # multiple returns
extern fn host_helper(x: f32[D]) -> f32[D]     # provided by the host (C ABI)
```

Parameters and returns are tensors or scalars. A tensor parameter may be a
`trit`/`i4`/`i2`/`fp8`/`fp16` *storage* tensor (weights); it is passed as a
packed pointer.

A parameter prefixed with `rw` is a **caller-owned mutable buffer**:

```veloce
fn append(rw cache: f32[CT, D], pos: i32, row: f32[1, D]) -> f32[1, D] {
    cache[pos] = row        # writes through to the caller's memory
    return row
}
```

The buffer is never allocated by the generated code and never copied in or
out, so a host loop can keep it alive across calls — that is how a KV cache is
built (`examples/kv_decode.vel`). Only `rw` parameters and `let` bindings can
be written to. The index may be an expression (`cache[pos + 1] = k[1]`), which
is what lets one call write a whole chunk of rows.

A cached decoder that consumes `T` tokens per call passes the attention mask as
`i32[T, CT]` — one row per query row, so row `r` at position `pos + r` may see
`pos + r` while row `r-1` may not. That is the per-row `softmax` form below;
a 1-D mask would give every row the same visible slots.

## Statements

```veloce
let x = expr            # mutable binding (reassignable)
const y = expr          # immutable binding
let a, b = fn(...)      # multiple binding from a multi-return call
x = expr                # assignment (target must be `let`)
v[i] = expr             # element write (1-D), or whole-row write on a 2-D tensor
m[i, j] = expr          # element write on a 2-D tensor
return expr
return a, b
if cond { ... } else { ... }
while cond { ... }
break
continue
```

`for` loops do not exist. Use declarative tensor operations instead.

## Expressions

* Arithmetic: `+ - * / // %`, unary `-`, `!`, comparisons, `&&`, `||`.
* Casts: `f32(expr)`, `i32(expr)`.
* Indexing: `v[i]` (element of 1-D, or row of 2-D), `m[i, j]` (element of 2-D).
* Matrix multiply: `a @ b` (float weights) — synonymous with `matmul(a, b)`.

### Tensor builtins (declarative)

| Builtin | Signature | Notes |
|---------|-----------|-------|
| `matmul(a, b)` / `a @ b` | `[M,K] @ [K,N] -> [M,N]` | float weights |
| `matmul_trit(x, w)` | `[M,K], trit[N,K] -> [M,N]` | **add/sub only**; `w` is `[out, in]` |
| `matmul_i4(x, w)` | `[M,K], i4[N,K] -> [M,N]` | 4-bit signed weights, 2 per byte; `w` is `[out, in]` |
| `matmul_i2(x, w)` | `[M,K], i2[N,K] -> [M,N]` | 2-bit signed weights, 4 per byte, values in `[-2, 1]` |
| `matmul_fp8(x, w)` | `[M,K], fp8[N,K] -> [M,N]` | E4M3 weights, 1 byte each, decoded to f32 in the dot |
| `matmul_i4g(x, w, s)` | `[M,K], i4[N,K], f32[N,G] -> [M,N]` | per-group scales; `G` must divide `K` |
| `matmul_i2g(x, w, s)` | `[M,K], i2[N,K], f32[N,G] -> [M,N]` | per-group scales; `G` must divide `K` |
| `matmul_fp8g(x, w, s)` | `[M,K], fp8[N,K], f32[N,G] -> [M,N]` | per-group scales; `G` must divide `K` |
| `matmul_trit_s(x, w, s)` | `[M,K], trit[N,K], f32[N] -> [M,N]` | one scale per output row |
| `matmul_i2_s(x, w, s)` | `[M,K], i2[N,K], f32[N] -> [M,N]` | one scale per output row |
| `matmul_fp8_s(x, w, s)` | `[M,K], fp8[N,K], f32[N] -> [M,N]` | one scale per output row |
| `rmsnorm(x, w)` | `[T,D], [D] -> [T,D]` | row-wise RMS norm with gain |
| `silu(x)` / `relu(x)` | `[..] -> [..]` | activation |
| `softmax(x)` | `[T,N] -> [T,N]` | row-wise softmax |
| `softmax(x, mask)` | `[T,N], i32[N] -> [T,N]` | masked row softmax: `mask[i] == 0` hides column `i` (probability exactly 0, excluded from the max and normaliser) |
| `softmax(x, mask)` | `[T,N], i32[T,N] -> [T,N]` | per-row mask: mask row `r` applies to scores row `r` (per-head causal), so different rows may hide different columns. The mask must be `i32`; other integer dtypes are rejected rather than reinterpreted |
| `transpose(x)` | `[R,C] -> [C,R]` | |
| `rope(x)` | `[T,D] -> [T,D]` | rotary position embedding |
| `embedding(table, idx)` | `[V,D], i32 -> [1,D]` | single token lookup |
| `embedding_seq(table, ids)` | `[V,D], i32[T] -> [T,D]` | batched token lookup |
| `meanpool(x)` | `[T,D] -> [1,D]` | mean over sequence axis |
| `argmax(x)` | `[..] -> i32` | index of max |
| `zeros(n)` / `zeros(r,c)` | -> tensor | zeroed activation |

Elementwise `+ - * /` work between same-shape tensors, tensor⊕scalar, and
2-D⊕1-D (bias broadcast across rows).

## Semantics & guarantees

* **Deterministic** — identical inputs produce bit-identical outputs.
* **Zero heap allocation** — every activation lives in a per-function `static`
  arena sized at compile time; buffers are reused across non-overlapping
  lifetimes.
* **C ABI** — each function compiles to `veloce_<name>(...)` with C types, so it
  links into C/C++/Rust/Go/Python `ctypes` hosts directly.

## Honest scope notes

* **v1.0 compute model**: weights are quantized (`trit`/`fp16`) and decoded
  during the kernel; activations are `f32`. Arithmetic in `f32` is not an
  "approximation" of the PRD — it is the standard low-bit inference design
  (quantize storage, accumulate in float).
* **Every PRD dtype is implemented end to end.** `i4`: `pack_i4`/`veloce_pack_i4`
  store two signed nibbles per byte (low nibble = element 2k, high = 2k+1),
  `veloce_matmul_i4` lowers through a 256×4 signed-nibble LUT.
  `i2`: `pack_i2` stores four signed 2-bit values per byte (values in [-2,1]),
  `veloce_matmul_i2` decodes through a 256×4 LUT with an AVX2 path.
  `fp8`: `pack_fp8` stores one E4M3 byte per value (bias 7, max 448); the
  runtime decodes with a lazily built 256-entry table, so an E4M3 checkpoint
  maps zero-copy and is expanded during the dot product.
  `test_i4_matmul_bit_exact`, `test_i2_matmul_numeric` and
  `test_fp8_matmul_numeric` check each one is bit-identical across 1/2/4
  threads and across the `.veloce` roundtrip. Measured max |err| vs a float64
  reference: 5.6e-6 (i2, K=1003) and 4.3e-6 (fp8, K=517).
* **Group- and row-scaled variants** exist for every low-bit dtype.
  `matmul_i4g`/`matmul_i2g`/`matmul_fp8g` take `f32[N, groups]` and share one
  typechecker rule and one lowering path; `matmul_trit_s`/`matmul_i2_s`/
  `matmul_fp8_s` take one scale per output row. The group count must divide
  the inner dimension exactly — a ragged count has no single group size, so it
  is rejected at compile time rather than silently scaling the wrong slices
  (`test_group_scaled_rejects_ragged_groups` covers all three kernels).
* **KV cache (FR-2.1 scope)**: a tensor parameter declared `rw` is a
  caller-owned mutable buffer, and `cache[pos] = row` stores a whole row into
  it, so a host loop can keep keys/values across calls. `examples/kv_decode.vel`
  plus `examples/run_kv_decode.py` decode five tokens this way (max |err|
  7.7e-7 per token, 1.0e-6 for the cached attention). Attention masking is a
  first-class builtin: `softmax(scores, mask)` with an `i32` mask (non-zero =
  participates) excludes hidden entries from both the row maximum and the
  normaliser, so a hidden entry contributes exactly zero whatever it holds —
  a stale cache row, `NaN` or `±1e30` cannot reach the result
  (`test_masked_softmax_builtin` poisons the hidden columns with exactly
  those values). A fully masked row returns zeros, not `NaN`.
  A 1-D mask is broadcast to every row; a 2-D `i32[T,N]` mask is *per row*
  (mask row `r` for scores row `r`, i.e. a per-head causal mask), which the
  lowering selects by mask rank — reading a 2-D mask as 1-D used to apply
  row 0 to every row and produce a plausible but wrong distribution. The
  mask dtype is `i32` only; `i8`/`i64`/`i2` are rejected instead of being
  reinterpreted as 32-bit words (`test_masked_softmax_per_row_mask`,
  `test_softmax_mask_rejects_bad_shape_and_dtype`).
  The cached decoder generated by `veloce/lmmodule.py` now passes a **2-D**
  mask (`i32[T, CT]`, one row per query row in the chunk) and decodes `T`
  tokens per call, writing `ck[pos + r] = k[r]`/`cv[pos + r] = v[r]` for every
  row. With `T > 1` the mask rows genuinely differ (row `r` may see `pos + r`,
  row `r-1` may not), so the per-row kernel is reached end to end and a
  broadcast mask is observable in the output. `test_cached_decode_attention_mask`
  decodes six tokens in chunks of 1, 2 and 3 through a 1-, 2- and 3-layer
  decoder against a strictly causal float64 reference (forcing the broadcast
  kernel makes it fail at `max|err| = 8.07`), and
  `test_cached_decode_mask_hides_garbage_slots` starts every cache row at
  `±1e30` and still matches that reference bit for bit (`max|err| = 5.80` if
  the mask stops hiding the unwritten slots).
* **FR-4.2 threading policy**: work is split over *independent output*
  elements only (rows for matmul/rmsnorm/softmax, elements for elementwise
  ops), never over a reduction axis, which is why bit-exact determinism is
  preserved. Kernels below the L2-cache threshold stay serial to avoid team
  launch overhead. `VELOCE_POOL=0` forces a serial build; `VELOCE_THREADS=n`
  pins the worker count, `VELOCE_PAR_MIN` (default 1024 output elements) sets
  the smallest problem that is worth a fork-join, and `VELOCE_PAR_GRAIN`
  (default 512 elements) is the largest chunk one worker may be handed: the
  grain is a *byte* budget (L2/4) expressed in items, so a loop of 308
  six-kilobyte tiles splits four ways instead of collapsing onto one lane.
  Applying that floor in elements alone was wrong for exactly this reason --
  see the 2026-11-20 entry above.
* **Measured performance (4-vCPU shared VM, load average ~2.2)**: the AVX2
  trit GEMV decodes 5 trits per byte with a 256-entry float LUT and works on
  four output rows per pass, reaching ~8.8–9.3 GMAC/s on one thread and
  19.7–23.0 GMAC/s on four (2.2–2.5×), i.e. 3.9–4.6 GB/s of packed weights:
  **22–31% of the host's real streaming peak (12.6–20.8 GB/s at 4 threads)**,
  not the 81–97% an earlier revision claimed — that figure compared a
  single-threaded scalar probe against a four-thread SIMD kernel.

  The four-row pass is what bought that. Flat base-3 packing puts row j at byte
  `(j*K)/5`, slot `(j*K)%5`, so rows only share an `x` window when they are in
  the same byte phase; the kernel therefore runs rows `j, j+p, j+2p, j+3p`
  (`p = 5/gcd(K,5)`) and hands one pair of 32-byte `x` loads to four LUT loads
  and four FMAs, instead of re-reading the whole `x` vector once per output
  neuron. Measured back to back in one process by
  `benchmarks/bench_gemv_roofline.py`, that is 1.33× (K=4096), 1.30× (K=1536)
  and 1.34× (K=1024), medians of three runs, over the one-neuron-at-a-time
  kernel; end to end it is 23.6 tok/s / 42.3 ms per token against 22.3 tok/s /
  45–50 ms before.

  **Two tokens per weight pass.**  A chunked decode multiplies the same packed
  matrix by two x vectors; running the one-row kernel twice streamed the
  matrix twice.  `veloce_trit_dot4x2_avx2` loads each packed byte and its
  32-byte LUT row once and feeds both query rows from it (same four-phase
  row groups as the one-row kernel), and `veloce_matmul_trit` dispatches
  `M == 2` onto it.  Measured with the same microbench that produced the
  one-row numbers, 100 reps, one thread: 4096² **7.59 → 10.71 GMAC/s per
  token** (2.21 → 1.57 ms), 1536×4096 5.4 → 6.6-9.4 GMAC/s, i.e. 1.25-1.41×
  per token.  Each (query row, neuron) keeps the one-row kernel's two
  accumulator chains and reduction order, so the result is **bit-identical
  to two `M == 1` passes** -- `test_trit_matmul_two_rows_share_one_weight_pass`
  checks that with `memcmp` on two different `x` rows, at K = 1003 (5-row
  phase stride) and K = 1024 (single phase), plus a float64 reference.  The
  single-stream projection is unchanged by this (it decodes one token at a
  time); it pays off when a caller decodes a chunk, as the cached decoder
  does.

  **Four tokens per weight pass.**  The same idea cannot be extended by simply
  widening the row group: four output rows * four query rows is 32 vector
  accumulators (4 queries × 4 rows × 2 chains), twice what AVX2 has, and `M ==
  3/4` therefore fell back to the per-row path, streaming the whole matrix once
  per token.  `veloce_trit_dot2x4_avx2` instead pairs **two** output rows with
  **four** query rows (16 accumulators) and shares each packed byte and its LUT
  row across all four; `veloce_matmul_trit` dispatches `M == 4` onto it, with a
  work item covering 2*period rows instead of 4*period.  Weight traffic per
  token is a quarter of the per-row path and a half of the two-query kernel.
  Measured on 4096², three runs, one thread (the stable configuration; four
  threads on this shared VM vary by 2× run to run): **1.94 ms per token for
  `M == 1` vs 1.19 ms for the four-query pass, 8.6 → 13.5 GMAC/s per token
  (1.63×)** and 1.6× the matrix bytes per second the one-row kernel streams.  At
  four threads the best-of-10 pairs measured 0.50 vs 0.65 ms/token (1.3×), with
  higher spread.  Per (query row, neuron) the two accumulator chains and
  reduction order are unchanged, so `M == 4` is **bit-identical to four `M == 1`
  passes** -- `test_trit_matmul_four_rows_share_one_weight_pass` pins that with
  `memcmp` at K = 1003/512/1024/1536 over whole tiles, plus a float64
  reference, and fails if the second row of a pass decodes the first row's
  bytes (mutation-verified).  `M == 3` still takes the per-row path; it needs a
  three-query pass (or one two-query pass plus one row) to share as well.

  The kernel is still *decode* bound, and the reason is now narrower: every
  packed byte costs a byte load plus a 32-byte LUT load for five useful values,
  and on this EPYC (128-bit FP units, 32-byte loads split in two) that is about
  three load slots per five MACs — ~3.3 MAC/cycle, which is where the kernel
  sits. A dense f32 FMA still reaches 1.5–2× the GEMV's MAC rate, and a pure
  read of the same packed bytes is 23–36× faster. A 7B-shaped layer compiled by
  `velocec` runs at 35.2 GMAC/s (5.44 tok/s for 32 layers) and the projected
  single-stream decode is 4.03 tok/s. A correct bandwidth roofline on this VM
  is 14.8 tok/s (19.5 GB/s measured), so the PRD's 15 tok/s target is only
  reachable *if the decode overhead is removed* — it is not a hardware wall,
  and the honest status is "FAIL today, real headroom".
* **End-to-end mid-size model** (`benchmarks/bench_midi_lm.py`): a genuine
  275.6M-ternary-parameter decoder (6 layers, d=1536, ffn=6144, V=32000,
  T=1 without KV cache) built with the production packing code, written as a
  153.5 MB `.veloce` file and run from a memory map. The module itself is
  rendered by `veloce/lmmodule.py` from a shape config, so the same command
  measures other sizes (`--config D=2048 --config F=5632 --config layers=7`,
  i.e. `make bench-midi-05b`); `examples/midi_lm.vel` is that renderer's
  default-config output and `test_default_render_matches_example` fails if the
  two drift. Measured in the committed artefact (`measured_at`
  2026-11-20T21:30Z, host load 1.5): **33.7 tok/s on one thread** and
  **62.9 tok/s on four** for the eager path, **63.6 tok/s** on four threads
  with the KV cache (32 tokens, chunks of two, 15.7 ms/token, rel err 1.3e-6,
  1.01x the eager path in the same run). Until the chunk-grain fix of the same
  day, four threads ran the whole decode inside one worker and were *slower*
  than one (15.4 vs 30.5 tok/s); the split now really happens, so the cached
  decode scales 1.89x from one thread to four. The logits match a NumPy
  reference to 1.4e-6 relative error and hash identically at every thread
  count.

* **The parallel split was silently a single worker** (fixed 2026-11-20).
  `veloce_parallel_for_sized` computed `chunk = ceil(n/lanes)` and then clamped
  it up to `VELOCE_PAR_GRAIN` (512 *elements*), so any loop with fewer than
  512*lanes items handed every item to worker 0 and left the caller empty:
  a two-row 4096² trit GEMV with `VELOCE_THREADS=4` ran at **1.06 CPUs
  utilised** and was 1.5× *slower* than one thread. The same term vetoed
  1536-wide trit tiles outright (`bytes_per_item < 8192`), so most of the
  275.6M decoder never forked at all. The grain is now a byte budget (L2/4,
  expressed in items, capped by the element floor) and the per-item size no
  longer vetoes a split; `test_parallel_for_hands_every_lane_work` counts
  distinct workers and asserts every item ran exactly once (with the old
  formula it reports `lanes=1 covered=205` and fails). Measured on the
  committed artefacts: trit GEMV 4096² one→four threads **9.19 → 26.13 GMAC/s
  (2.84×)**, the 275.6M decoder **25.1 tok/s on one thread and 62.9 on four**
  (the previous artefact measured 15.4 on four threads, i.e. *slower* than its
  own 22.3 one-thread run), and its KV-cached decode **33.7 → 63.6 tok/s
  (1.89×)**; the 7B-class projection moved from 3.04 to **4.03 tok/s** against
  a 14.8 tok/s bandwidth ceiling.

## Model capability defaults

Every `.veloce` export carries a capability model card (see
`docs/model-capabilities.md`). The default profile declares four pillars —
deeper specialist knowledge, richer world understanding, stronger coding and
agentic behaviour, and real-world task focus — each with status `declared`,
`trained`, or `verified`. `trained`/`verified` require attached evidence, and
`veloce.capabilities.validate_model_card` rejects overclaims. This is a
declaration contract, not a capability claim: both shipped checkpoints (the
27k-parameter QAT classifier and the 275.6M throughput demonstrator) remain at
`declared` for all four pillars, because Veloce is the inference compiler and
the capabilities come from the trained model.

===== docs/model-capabilities.md =====
# Model capability defaults

Veloce is an inference compiler and runtime, not a model. It cannot add
knowledge, world understanding, or agentic skill by itself — those come from
the trained model: pretraining data, parameter count, post-training, and
evaluation. What Veloce standardises is how a model *declares* its intended
capabilities, so a `.veloce` file always travels with an honest, machine-
readable model card instead of a marketing claim.

Every Veloce-built model carries a **default capability profile** with four
pillars:

| Pillar | What it means | Delivered by | Typical eval |
|--------|---------------|--------------|--------------|
| `specialist_knowledge` | **Deeper knowledge** — more accurate answers in specialist topics: domain terminology, facts, procedures. | Pretraining coverage + capacity; domain continued pretraining / SFT. | MMLU-Pro, GPQA-Diamond, domain held-out QA |
| `world_understanding` | **Richer world understanding** — real-world context reasoning, not just text patterns: grounded entities, events, physical/social context, situational inference. | Broad, diverse corpora; grounded/multimodal context; world-model objectives. | RealWorldQA, MMMU, Agents' Last Exam (knowledge work) |
| `coding_agentic` | **Stronger coding and agentic** — plan, call tools, complete multi-step tasks: repo-scale changes, shell/tool use, error recovery. | Code corpora, execution feedback, tool-use traces, RL in environments. | SWE-bench Verified, Terminal-Bench, tau-bench |
| `real_world_tasks` | **Real-world task focus** — complex coding, front-end builds, professional workflows; end-to-end deliverables. | Task distributions from real user workflows; environment scaling; deliverable-level evaluation. | SWE-bench Multimodal, WebArena, OSWorld |

## Status semantics

Each pillar in a model card has a `status`:

| Status | Meaning | Requires |
|--------|---------|----------|
| `declared` | The model targets this pillar. **Not** a capability claim. | nothing |
| `trained` | The training pipeline included this pillar's data/objectives. | non-empty `evidence` |
| `verified` | Measured benchmark results exist. | non-empty `evidence` |

The defaults are conservative: a freshly exported model declares all four
pillars at status `declared`. `veloce.capabilities.validate_model_card`
rejects `trained`/`verified` without evidence, unknown pillars, and unknown
statuses, so a model card cannot silently overclaim. The toy classifier from
`make train` and the untrained 275.6M throughput demonstrator from
`make bench-midi` both remain at `declared` for every pillar.

## Model card in the `.veloce` file

`weights.save_veloce(..., model_card=card)` embeds the card in the `.veloce`
manifest; `weights.VeloceFile(path).model_card` reads it back, and

```bash
./velocec model-card examples/tiny_lm.veloce
```

prints it. Build a card with `veloce.capabilities.make_model_card`:

```python
from veloce.capabilities import make_model_card

card = make_model_card(
    "my-model",
    model_type="ternary-transformer",
    params={"ternary": 1_500_000_000},
    training={"status": "trained", "dataset": "..."},
    capabilities={
        "coding_agentic": {
            "status": "trained",
            "evidence": ["SFT on 120k tool-use trajectories"],
        },
    },
)
```

Pillars not passed stay `declared`. A serving stack can therefore reject a
model whose `coding_agentic` status is `declared` when the deployment needs an
agentic model — or route it to an evaluation queue first.

## What Veloce provides vs. what the model must provide

| Layer | Provided by Veloce | Provided by the model |
|-------|--------------------|------------------------|
| Packed low-bit weights, trit/i4 kernels | ✅ | |
| Zero-copy `.veloce` mmap, static arena | ✅ | |
| Caller-owned KV cache (`rw` tensors, row stores) | ✅ (`examples/run_kv_decode.py`) | |
| Attention masking over unwritten cache slots | ❌ (softmax has no mask yet) | |
| Tool-call markers, chat template | ❌ (runtime-agnostic; host handles) | |
| Specialist knowledge, world grounding | | ✅ data + scale |
| Planning, tool use, multi-step agency | | ✅ post-training + RL |
| Real-world deliverable quality | | ✅ data + evaluation |

The table matters: a 275.6M ternary demonstrator compiled by Veloce is a
*throughput* artifact, not a capable assistant. Claiming the four pillars as
delivered features of the compiler would be dishonest; declaring them as the
default target profile and attaching evidence per checkpoint is the contract
this repository can actually keep.

===== docs/training-framework.md =====
# Training framework (design + current state)

Goal: **one model definition, two backends** — a NumPy reference for gradients and
Veloce-compiled C for speed. No PyTorch, no autodiff library; the graph is ours and the
compiler is ours.

```
        model builder (Python)                     the one source of truth
                 │
     ┌───────────┴────────────┐
     ▼                        ▼
 NumPy forward +          Veloce DSL emitter
 analytic grads           (forward + backward source)
 (reference, tests)              │
                                 ▼
                        veloce.compile_file → C11
                                 │
                                 ▼
                     shared lib (ctypes) or standalone trainer
                                 │
                                 ▼
                  Adam in the driver · ternary export (.veloce)
```

## What exists today

- `veloce/train/graph.py` — tensor graph with ops:
  `matmul, add, mul, transpose, rmsnorm, silu, softmax, mean_rows, embedding,
  cross_entropy, sum_sq` — each with a NumPy forward and an analytic reverse-mode rule.
- `tests/test_train.py` — three gradient checks against central finite differences:

| test | what it covers | worst relative error |
|---|---|---|
| `test_mlp_single_block` | embedding → mean-pool → rmsnorm → matmul → silu → matmul → CE | 2.4e-4 |
| `test_softmax_transpose_mul` | transpose, mul, softmax, CE | 1.7e-4 |
| `test_rmsnorm_rows` | rmsnorm over rows, weighted loss | 5.1e-4 |

Run: `python tests/test_train.py` (needs `numpy` from `.venv`).

## What is not built yet

1. **DSL emitter** — graph → `.vel` source for `forward` and `backward`. The op set above
   maps onto DSL builtins (`matmul`, `rmsnorm`, `silu`, `softmax`, `transpose`,
   `embedding`), so the emitter is a printer plus a schedule of `let` bindings; the
   backward needs transposed matmuls and the saved `inv` / `sig` / `p` tensors as extra
   inputs.
2. **Driver** — compile the emitted module to a shared object with a fixed ABI
   (`void fwd(float* out, const float* p, const int* ids)`), call it from Python with
   NumPy buffers, and run Adam there. Alternative: emit a `train.c` with the loop inside.
3. **Causal attention + mask** — `softmax_mask` exists in the DSL; the graph needs a
   `mask` op and its gradient rule (`p * (g - sum(g·p))` under the same mask).
4. **Data path** — BPE tokenizer (32k), shard writer, sequence sampler.
5. **Ternarisation on export** — `weights.pack_trits` already exists; the trainer must
   keep a float latent master copy (as `train_tiny_lm.py` does with straight-through).

## Phasing

| phase | deliverable | proof |
|---|---|---|
| 1 (done) | graph + analytic gradients | 3 gradient checks vs finite differences |
| 2 | DSL emitter for this op set | emitted module compiles; C forward matches NumPy to 1e-6 |
| 3 | backward emission + ctypes driver | compiled backward matches NumPy gradients; one Adam step lowers loss |
| 4 | causal LM block (mask, positions) | loss decreases on real text, not synthetic |
| 5 | tokenizer + shards + ternary export | trained tiny model runs through `veloce` inference |
| 6 | scale | 1B remains an inference target until GPU budget exists |

## Design decisions worth keeping

- **Three files of state per tensor**: value, grad, and the saved forward intermediates
  needed by the rule. No tape of closures — explicit attrs make the emitter trivial.
- **Ops are closed set.** Adding an op means adding forward + rule + emitter line + a
  gradient check. The test file is the contract.
- **Float latent, ternary export.** Training never uses trit weights; it ternarises at
  export, exactly like `examples/train_tiny_lm.py`.
- **The gradient check is mandatory.** A wrong rule is invisible in the loss curve for
  hundreds of steps.

===== models/veloce-1b/README.md =====
# veloce_1b — 1B-class ternary decoder

The largest shape Veloce has compiled and executed end to end. Built to answer one
question: **does the runtime still work, and how fast is it, at 1B parameters on a
4-vCPU box with no GPU?**

Reproduce (regenerates weights + module, runs both benchmarks):

```bash
make model-1b
```

## Shape

| | |
|---|---|
| vocab | 32 000 |
| d_model | 2 048 |
| ffn | 5 632 |
| layers | 18 |
| attention | 4 × D×D per layer (`wq wk wv wo`) |
| ffn | 3 × F×D per layer (`w1 w2 w3`) |
| ternary params | **990 380 032** (924.8M layers + 65.5M head) |
| fp16 embedding | 65 536 000 values (131.1 MB) |
| **total parameters** | **1 055 916 032** (≈1.06B) |
| weight file | **329.3 MB** (198.1 MB trits + 131.1 MB embed + 0.16 MB norms) |
| packing | 5 trits/byte ≈ 1.6 bits per trit |

Arena peaks from the compiler: `attn` 16 448 B, `layer` 122 880 B, `forward` 144 384 B —
activation memory is irrelevant next to the weights, which is the whole point of the
low-bit design.

## Measured on this machine (4 vCPU, 7.8 GB RAM, warm page cache)

Single-token forward, no KV cache (`--iters 5`, 5 separate runs per thread count):

| threads | median of medians | best run median | best single pass |
|---|---|---|---|
| 1 | 137.9 ms → **7.25 tok/s** | 131.7 ms → 7.59 tok/s | 126.7 ms → 7.89 tok/s |
| 2 | 80.5 ms → **12.42 tok/s** | 77.9 ms → 12.84 tok/s | 69.9 ms → 14.31 tok/s |
| 4 | 87.1 ms → **11.48 tok/s** | 46.6 ms → 21.47 tok/s | 40.4 ms → 24.74 tok/s |

KV-cache decode, 32 tokens through a 64-slot cache per layer:

| threads | total | ms/token | tok/s |
|---|---|---|---|
| 1 | 5 304 ms | 165.8 | 6.03 |
| 2 | 3 152 ms | 98.5 | 10.15 |
| 4 | 2 909 ms | 90.9 | **11.00** |

Determinism: **PASS**. One logit hash across all thread counts (`cfb675cd4012f43a`),
byte-identical reruns, `nonfinite=0`, argmax 31195.

## What the numbers actually say

- **1 thread is the honest baseline** (7.2–7.9 tok/s). It barely varies (≤8%).
- **4 threads is unstable on this box**: medians between 46.6 ms and 148.8 ms across
  five runs — a 3.2× spread, because 4 vCPU are shared with nginx, the agent services
  and my own background jobs. The 21.5 tok/s run is real, but it is not the number to
  plan on.
- **The KV cache does not help at this size** (11.0 vs 13.1 tok/s in the same process,
  0.84×). Decoding one token still streams 198 MB of trits; skipping attention work
  saves almost nothing, while the cached module adds a per-layer call.
- **Bandwidth efficiency is ~24%**: the model sustains 2.51 GB/s against a 10.56 GB/s
  streaming probe. The gap is per-layer dispatch overhead, not the memory system —
  which is where the next 2–3× lives (wider kernels, fewer passes per layer, chunked
  multi-token weight reuse).

## Honest limitation: these weights are initialised, not trained

`bench_midi_lm.py` generates weights deterministically from a per-tensor seed. That is
exactly right for measuring a runtime — the numbers above are real — but the model has
**no language ability**. Sampling from it produces tokens, not sentences.

Training a real 1B model is not possible on this machine: an industry-minimum
(Chinchilla) 20B-token run at 1B parameters needs GPU-days, while this box runs one
token in ~0.14 s. What this repository can honestly claim today is the *inference*
side: the compiler emits working C for 1B ternary weights, it fits in a 329 MB mmap,
runs deterministically across thread counts, and reaches 7–12 tok/s single-stream on
4 vCPU. Everything about quality is still to be earned elsewhere.

## Files

- `veloce_1b.vel` — the generated module source (5.3 KB, 18 unrolled layers).
- `veloce_1b.veloce` — weights, 329 MB, generated by the benchmark (not committed;
  `make model-1b` rebuilds it in ~23 s).
- `../../benchmarks/veloce_1b_results.json` — eager numbers.
- `../../benchmarks/veloce_1b_cached.json` — cached decode numbers.
