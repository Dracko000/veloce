# veloce_1b — 1B-class ternary decoder

The largest shape Veloce has compiled and executed end to end. Built to answer one
question: **does the runtime still work, and how fast is it, at 1B parameters on a
4-vCPU box with no GPU?**

Reproduce (regenerates weights + module, runs both benchmarks):

```bash
make model-1b
```

## Shape

| | |
|---|---|
| vocab | 32 000 |
| d_model | 2 048 |
| ffn | 5 632 |
| layers | 18 |
| attention | 4 × D×D per layer (`wq wk wv wo`) |
| ffn | 3 × F×D per layer (`w1 w2 w3`) |
| ternary params | **990 380 032** (924.8M layers + 65.5M head) |
| fp16 embedding | 65 536 000 values (131.1 MB) |
| **total parameters** | **1 055 916 032** (≈1.06B) |
| weight file | **329.3 MB** (198.1 MB trits + 131.1 MB embed + 0.16 MB norms) |
| packing | 5 trits/byte ≈ 1.6 bits per trit |

Arena peaks from the compiler: `attn` 16 448 B, `layer` 122 880 B, `forward` 144 384 B —
activation memory is irrelevant next to the weights, which is the whole point of the
low-bit design.

## Measured on this machine (4 vCPU, 7.8 GB RAM, warm page cache)

Single-token forward, no KV cache (`--iters 5`, 5 separate runs per thread count):

| threads | median of medians | best run median | best single pass |
|---|---|---|---|
| 1 | 137.9 ms → **7.25 tok/s** | 131.7 ms → 7.59 tok/s | 126.7 ms → 7.89 tok/s |
| 2 | 80.5 ms → **12.42 tok/s** | 77.9 ms → 12.84 tok/s | 69.9 ms → 14.31 tok/s |
| 4 | 87.1 ms → **11.48 tok/s** | 46.6 ms → 21.47 tok/s | 40.4 ms → 24.74 tok/s |

KV-cache decode, 32 tokens through a 64-slot cache per layer:

| threads | total | ms/token | tok/s |
|---|---|---|---|
| 1 | 5 304 ms | 165.8 | 6.03 |
| 2 | 3 152 ms | 98.5 | 10.15 |
| 4 | 2 909 ms | 90.9 | **11.00** |

Determinism: **PASS**. One logit hash across all thread counts (`cfb675cd4012f43a`),
byte-identical reruns, `nonfinite=0`, argmax 31195.

## What the numbers actually say

- **1 thread is the honest baseline** (7.2–7.9 tok/s). It barely varies (≤8%).
- **4 threads is unstable on this box**: medians between 46.6 ms and 148.8 ms across
  five runs — a 3.2× spread, because 4 vCPU are shared with nginx, the agent services
  and my own background jobs. The 21.5 tok/s run is real, but it is not the number to
  plan on.
- **The KV cache does not help at this size** (11.0 vs 13.1 tok/s in the same process,
  0.84×). Decoding one token still streams 198 MB of trits; skipping attention work
  saves almost nothing, while the cached module adds a per-layer call.
- **Bandwidth efficiency is ~24%**: the model sustains 2.51 GB/s against a 10.56 GB/s
  streaming probe. The gap is per-layer dispatch overhead, not the memory system —
  which is where the next 2–3× lives (wider kernels, fewer passes per layer, chunked
  multi-token weight reuse).

## Honest limitation: these weights are initialised, not trained

`bench_midi_lm.py` generates weights deterministically from a per-tensor seed. That is
exactly right for measuring a runtime — the numbers above are real — but the model has
**no language ability**. Sampling from it produces tokens, not sentences.

Training a real 1B model is not possible on this machine: an industry-minimum
(Chinchilla) 20B-token run at 1B parameters needs GPU-days, while this box runs one
token in ~0.14 s. What this repository can honestly claim today is the *inference*
side: the compiler emits working C for 1B ternary weights, it fits in a 329 MB mmap,
runs deterministically across thread counts, and reaches 7–12 tok/s single-stream on
4 vCPU. Everything about quality is still to be earned elsewhere.

## Files

- `veloce_1b.vel` — the generated module source (5.3 KB, 18 unrolled layers).
- `veloce_1b.veloce` — weights, 329 MB, generated by the benchmark (not committed;
  `make model-1b` rebuilds it in ~23 s).
- `../../benchmarks/veloce_1b_results.json` — eager numbers.
- `../../benchmarks/veloce_1b_cached.json` — cached decode numbers.
